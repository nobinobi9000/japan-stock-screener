以下をそのままコピーして、実装エージェント(Claude Code等)に渡してください。

あなたは nobi-labo の3サービス(日本株スクリーナー / kabu-signal / Kabu Note)の再構築を担当するエンジニアです。以下の指示に従って修正を実施してください。

# ⛔ 絶対原則 — いかなる理由があっても変更・省略・妥協してはならない

以下の原則は本プロジェクトの根幹であり、実装の都合・工数削減・「その方が便利」という判断があっても**絶対に曲げてはならない**。原則と衝突する実装しか思いつかない場合は、勝手に代替案を実装せず、**必ず作業を停止して確認を求めること**。

## 原則1: 投資助言に該当する要素を一切作らない
- すべての通知・レポート・UI文言は「機械的な条件成立の事実表示」のみとする
- 禁止語(生成するすべての文言・コード内文字列・テンプレートに適用):
  「推奨」「おすすめ」「エントリーに」「買い時」「売り時」「狙い目」「〜すべき」「勝率」「利確ライン」「損切りライン」の提案
- 売買判断を示唆する表現を発見した場合は事実表示に書き換える(例:「強い買いシグナル」→「GC・MA200上向き・出来高急増が同日成立」)
- 勝率・期待リターン等のパフォーマンス数値は表示しない。バックテスト結果の掲載も禁止
- 損益アラートの閾値(±X%)は必ずユーザー自身が設定する。システム側からデフォルト推奨値を提示しない
- 判定ロジックは全ユーザー共通。ユーザー個別にロジックを変える機能を作らない

## 原則2: データ取得は1回、消費は複数(単一パイプライン)
- 銘柄データの取得・指標計算はスクリーナーのバッチ1箇所のみで行う
- signal・Kabu Noteは日次スナップショットを読むだけ。**いかなる理由でも銘柄データを独自に再取得するコードを書かない**
- signalの独自取得はTDnet適時開示のみ許可(スナップショットに存在しない情報のため)
- ユーザー数が増えても取得コストが増えない構造を維持する

## 原則3: 有料コンテンツを公開経路に置かない
- スナップショット・全銘柄レポートを GitHub Pages / publicリポジトリ / 認証なしURL に配置しない
- 有料コンテンツは非公開ストレージ＋認証付きAPI経由でのみ配信する
- 無料公開してよいのは「厳選3銘柄＋市場サマリー」のみ

## 原則4: 個人化された通知を共有チャンネルに流さない
- ユーザーのウォッチリスト・保有銘柄に基づく通知(signal)は、Discordの共有チャンネルに配信しない(他ユーザーに保有情報が見えるため)
- signalの通知はユーザー個別チャネル(PWA push・メール)のみ
- Discord共有チャンネルに流してよいのは全員同一内容(スクリーナーの市場スキャン結果)のみ
- 有料会員への到達手段を外部プラットフォーム(Discord等)に依存させない。重要連絡は必ず自前で保有するメールで届く構成とする

## 原則5: 沈黙による誤認を作らない
- バッチ失敗・データ欠損の日は「本日は配信なし/データ取得不可」を明示的に通知する
- 「通知が来ない＝異常なし」とユーザーが誤認する状態を設計上許さない
- 不完全なスナップショット(成功率が閾値未満)を「完成」として下流に流さない

## 原則6: ユーザーデータの分離
- 保有銘柄・取得単価・ウォッチリストは機微な金融情報として扱う
- DBにはユーザー間分離(Supabase使用時はRLS必須)を実装する
- 個人データをURLパラメータ・公開ログに含めない

# 実装タスク(この順序で実施)

## Phase 1: スクリーナーバッチの安定化
1. GitHub Actions の cron を毎時00分から半端な分にずらす(例: 16:07 JST起動。UTC換算に注意。東証大引け15:30以降であること)
2. 3,700銘柄の取得を matrix strategy で8〜10シャードに並列分割し、needs で集計ジョブに連結。目標: 起動から45分以内に完了
3. 営業日判定を「月〜金」からJPX営業日カレンダー(祝日・年末年始を含む)に変更

## Phase 2: 日次スナップショットの契約化
1. スナップショットのスキーマを確定: 全銘柄 × {終値, 9指標フラグ, スコア, 取得成否フラグ} ＋ {スキーマバージョン, 生成日時, 全体成功率}
2. 成功率が閾値(例: 95%)未満の場合は「不完全」フラグを立てる
3. 保存先を非公開ストレージ(Cloudflare R2 または Supabase)に変更。GitHub Pagesへのスナップショット配置を廃止(原則3)
4. 認証付き配信API(Cloudflare Workers等)を作成。無料公開分(厳選3銘柄＋サマリー)のみ静的公開を維持

## Phase 3: 統一アカウント基盤
1. Supabase Auth を土台に統一アカウント(nobi-labo ID)を新設
2. Discordユーザー / PWA push購読 / Kabu Noteアカウント / (将来)Stripe顧客ID を統一IDに紐付けるテーブル設計
3. エンタイトルメント(Free/Pro)判定を全サービスがJWT検証で共有できる構成にする
4. RLSでユーザー間データ分離を実装(原則6)

## Phase 4: Kabu Note 拡張
1. 保有銘柄とは別に「ウォッチリスト(未購入の監視銘柄)」機能を追加
2. スクリーナーのレポートから「ウォッチに追加」導線を実装
3. 株価の独自取得を廃止し、スナップショット参照に切替(原則2)
4. 株式分割・併合の検知と取得単価調整フロー(自動調整またはユーザー確認)を追加

## Phase 5: signal 改修
1. 全市場スキャンを廃止し、スナップショット × ユーザーのウォッチリスト/保有銘柄の突合型に変更(原則2)
2. 通知時刻を 21:00 JST に変更。起動時に鮮度ガード(スナップショットが当日かつ完全であることを検証。不合格なら15分間隔でリトライ最大N回、最終失敗時は管理者通知＋「本日配信なし」をユーザー通知)(原則5)
3. 売り側判定を追加(既存9指標の逆条件): デッドクロス / MA200割れ＋下向き転換 / 雲割れ・三役逆転 / BB−2σ割れ / OBV下降転換 / 出来高急増を伴う下落
4. TDnet照合に下方修正・減配・公募増資・特別損失の検知を追加
5. ユーザー設定型の損益アラート(取得単価±X%、閾値はユーザー入力のみ)(原則1)
6. 通知チャネルの役割分担を実装(原則4):
   - PWA push: signalの個人化通知(21:00のリアルタイム通知)の主チャネル
   - メール: 有料会員向けの確実な到達チャネル(日次レポートリンク、重要告知、障害通知)。送信基盤はResend等の低コストサービスを採用し、Phase 3の統一アカウントで取得するメールアドレスを利用する
   - Discord共有チャンネル: 無料層向けの市場スキャン配信(全員同一内容)とコミュニティのみ。個人化通知は実装しない
   - LINE・Telegram等への配信は実装しない(スコープ外)
7. 監視銘柄がスナップショットで取得失敗していた日は「本日データ取得不可」を明示通知(原則5)
8. JVQMの全市場スコア計算はスクリーナーパイプラインに移設し、スナップショットに列として追加(W点灯用)

## Phase 6: 文言総点検
以下を原則1の基準で全面書き換え。対象: LP(screener/signal/note)、HTMLレポートテンプレート、Discord配信テンプレート、push通知文面、FAQ
1. FAQ Q4(勝率)を削除し「予測・実績値を提供していない」旨の回答に差し替え
2. FAQ Q2を「スコアの見方」に書き換え(条件成立の集計であることを明記)
3. FAQ Q5の証券会社名と優位性言及を削除
4. サポート案内に「個別銘柄の売買判断・投資タイミングに関する質問には回答しない」を明記
5. LPの「エントリーに」「推奨」「最も信頼される」等をすべて事実表示に変換
6. kabu-signalの「指値目安」を削除
7. 売り側通知の文言も「手仕舞い条件成立」「下方修正を検知」等の事実表示のみとする

## Phase 7: 法務ページ
1. 特定商取引法に基づく表記ページを新設(Stripe導入前に必須)
2. プライバシーポリシーを改訂: 保有銘柄・取得単価・ウォッチリスト等の金融情報を扱う実態に合わせる
3. Discordサーバールールに「運営者は個別銘柄に関する質問に回答しない」「商用勧誘・有料情報販売の禁止」を追記

# 実装しないこと(スコープ外)
- Stripe課金の有効化(財務局への事前照会完了後に別途実施)
- 自動売買・注文連携機能(永久にスコープ外)
- yfinance→J-Quants移行はデータ取得層を差し替え可能な抽象化(インターフェース分離)だけ先に行い、移行自体は別タスクとする

# 完了条件
- 各Phaseの完了時に、変更内容と絶対原則1〜6への適合を自己点検した結果を報告すること
- 原則に抵触する既存コード・文言を発見した場合は、修正するか、判断に迷う場合は停止して報告すること
- 文言変更はすべて変更前/変更後の対照表として出力すること

**最重要**: 上記の絶対原則は、実装中にどれほど不便でも、どれほど「例外的にこの箇所だけは」と思えても、変更してはならない。原則を破る実装と、原則を守るが機能が減る実装の二択になった場合は、必ず後者を選ぶか作業を停止して確認を求めること。
